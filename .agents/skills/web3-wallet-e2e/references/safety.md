# Safety boundary

Normal wallet connection for a dedicated public test account and explicitly verified ordinary network switching may be approved. Verify native origin and the exact intended chain before any network-switch approval. Transactions, token approvals, typed data, personal signatures, login signatures, permits, sponsored operations, session keys and other authorization requests are never approved. This applies even to unfunded local fixtures. Inspection and rejection are the terminal actions.

Use an isolated browser profile, exclusive process lock, trusted pinned extension code and trusted reviewed app/test code. Never run untrusted PR code on a host holding wallets or secrets. Do not overwrite, clone or attach to a personal browser profile. The runner serializes its own use; Chromium's profile lock also protects against other processes. Never delete an uncertain lock to force a retry.

Wallet adapters expose readiness, native connection, public-state reads, request detection, inspection and rejection. Do not add an approval or signing method. Do not reuse a legacy adapter with submission capabilities without isolating its safe behavior. No generic wallet click steps, selector fallback, risk-warning dismissal, blind Next loops or RPC signing. A version-specific network switch must have its own audited nonfinancial route and controls. Unknown signature layouts are UNSUPPORTED and must remain unapproved. Closing a browser does not establish rejection or absence of submission.

Verify one native request of the expected type before inspecting. Verify the unique audited rejection button and its exact Reject/Cancel label. Reject only once; if the click times out, stop with unresolved cleanup. If inspection fails before rejection is attempted, attempt that known rejection control once. Do not dismiss unrelated or stale requests automatically: isolate their origin and stop.

Never request, import, export or log a recovery phrase/private key. A test-wallet unlock password may be injected through an operator's secret manager as WALLET_TEST_PASSWORD, or persisted when explicitly requested in an ignored owner-only (0600) local environment file outside the distributable skill; never as an argument or committed file. No screenshots, trace or console recording during onboarding or unlock. Do not capture whole wallet storage/background state or arbitrary DOM dumps. Traces disable screenshots, DOM snapshots and sources; review trace contents before sharing. App URLs and scenarios must contain no credentials or secret query values. The runner captures error categories and timestamps rather than raw console strings that may contain credentials. For detailed errors, manually retain only reviewed/redacted relevant messages.

Evidence is private (umask 077), gitignored, and should have a retention policy. Only public addresses appear in scenarios and reports. Verify redaction before uploading evidence to CI or a PR. CI jobs with actual profiles require trusted code, one job per profile, no retries and an available headed display when required. Unit tests may use synthetic UI objects; those are not real-extension validation.

Never assert `transactionsSubmitted: false` based solely on not clicking Confirm. Record zero intentional authorization actions and independently observed broadcast state separately. A before/after pending+latest nonce check on the exact account/chain is useful corroboration but cannot prove absence of every user operation, relayed transaction or offchain signature. Unexpected hashes, account activity or requests stop the campaign; never reconcile by sending another transaction.

An uncertain rejection leaves .state/<profile>/unresolved-request.json and blocks subsequent runner invocations. Only an operator may reconcile the actual wallet state and remove that marker after independent review. Do not delete it to retry.
