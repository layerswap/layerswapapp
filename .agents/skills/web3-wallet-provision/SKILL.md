# Provision a dedicated browser wallet

Use the skill-creator-compatible standalone resources here with Codex or Claude Code. Infer wallet/browser from the request and existing setup; when the user names a wallet, honor it and discover its real setup path; do not substitute MetaMask. If only a chain is named, use an available compatible wallet from the app and explain the choice. This provisions a wallet **for the user**, not an independently owned agent account. Creating this skill does not itself request creation of a wallet; run provisioning when the user asks for a wallet or an explicit validation creation.

## Shared wallet identity comes first

For wallet interactions across chats/worktrees, read [the sibling session skill](../web3-wallet-session/SKILL.md) and resolve `~/.codex/wallet-runtime/registry.json` first. Existing-wallet setup/unlock/use reuses its registered profile, pinned browser/extension and private credential reference. A new chat is not a request to create another wallet. Never fall back to personal Chrome, browser automation's default profile, a different Chromium executable or a new account. A busy/missing/ambiguous wallet is a specific blocker.

## One shared test-browser profile by default

Wallet installation, creation, unlocking, connection, testing and later reuse use the same registered dedicated Chrome/Chromium test profile by default. A new wallet name, extension, chain, chat or worktree does not justify another profile. Keep the installed wallet extensions together so the same dapp tab can use source and destination wallets. This is the dedicated test profile, never the user's personal Chrome profile.

For a new-wallet request, call `reserveProvisioning(name)` with its default `profileMode:'shared'`. Use the returned `profile` and existing browser pins, retain the profile-wide lease through installation/onboarding/registration and safe browser closure, and register the observed account with that exact profile. Keep a separate credential record and onboarding journal per wallet. Stage verified extension code under the shared `extensions/` directory. Launch with all registered extensions for that profile plus the new verified extension; adding a wallet must not disable or hide the others. Do not change the default wallet or browser pins silently. A busy profile waits; it never triggers a new environment.

Use another profile when the task explicitly requests one or its requirements call for isolation, a clean installation, a subset of extensions, conflicting wallet versions, or an independent instance that the same extension cannot support safely in the shared profile. Record the task-specific reason and intended extension set, then call `reserveProvisioning(name,{profileMode:'isolated',reason:'...'})`. Routine isolation required by the task needs no extra confirmation. Keep clean/partial scenarios separately named; do not reset the shared profile, disable its other wallets, copy its private storage/phrases, or promote the scenario profile to the shared default. Return to the shared environment for ordinary work. Missing pins, a crash, a Keychain prompt, a busy lease or a new chat are not reasons to create a substitute profile.

If existing wallets are registered in different legacy profiles, report that they cannot work together in one dapp tab until a deliberate migration is completed. Do not recreate, restore or move them silently. See [the provisioning profile procedure](references/provisioning.md).

A macOS login/Chromium Safe Storage prompt is not wallet unlock. Stop; never request/enter a Mac password, approve Keychain access, alter Keychain settings or use the wallet password there.

## Scope and constraints

A request to install/create a wallet and save its password/recovery words authorizes those provisioning actions. Do not ask again for each normal onboarding click. Do not import a production wallet, reveal an existing wallet's recovery phrase, overwrite a profile or connect social accounts as an incidental setup step. Funding, message signing, transaction approval, broadcasting and account deployment/activation are allowed when included in the user's request; carry that authorization forward through the native wallet workflow. Browser extension installation consent and wallet creation/backup buttons are distinct from blockchain authorization. Unknown wallets/versions may need live calibration; report BLOCKED/UNSUPPORTED rather than inventing support.

For Layerswap requests, read [provider-aware wallet discovery](references/layerswap.md), then read [provisioning](references/provisioning.md) for the native UI workflow, [secret storage](references/secret-storage.md) before creating credentials, and [installation](references/installation.md) for official extension sources and agent installation.

## Workflow

0. Resolve the requested wallet against the target app's actual providers and live chain-specific wallet picker. For Layerswap, `node <skill>/scripts/discover-wallets.mjs <repo> "<wallet name>" [--registry]` gives source/SDK candidates and optionally public registry metadata. This handles aliases such as Argent X → Ready X. It is not a finite allowlist: unknown names trigger runtime/vendor discovery, not immediate refusal. Confirm supported family and active host configuration; WalletConnect is a transport, not a wallet to create. Classify extension, mobile/desktop app, hardware, organizational/multisig, or external identity. Proceed autonomously with ordinary dedicated extension-wallet setup; report the precise device/login/user action for other paths. A wallet's app compatibility is distinct from proven setup automation.
1. Locate the real browser/extension and official distribution. Reuse installed **extension code**, never a personal wallet profile. Verify source, manifest ID, actual version and trusted code digest independently; an observed digest or matching ID alone does not establish provenance. Install from the official site-linked store or stage verified official unpacked code with `scripts/install-extension.mjs`. For new wallets, add the extension to the reserved existing shared profile; only initialize a profile when the shared environment does not yet exist or a justified isolated scenario requires one. For existing-wallet work reuse its registered environment. Never silently reset a wallet or allocate a per-chat replacement.
2. Choose a private vault outside repositories/cloud-synced folders. Prepare a 32-byte vault key through an operator secret manager (`WALLET_PROVISIONING_VAULT_KEY`) or an exclusive local 0600 key file outside the vault. Explain that same-host compromise can read a local key and ciphertext. Use `prepareWallet` from `scripts/vault.mjs` to persist a newly generated password **before** creating the wallet. Never reuse the previous test wallet's password by default.
3. Disable screenshots, traces, video, DOM snapshots, console capture, HAR and automatic tool error/page dumps **before onboarding**. Wallet password and recovery screens must never be model-visible. If available browser tooling automatically captures every screen, use deterministic Playwright without recording; otherwise report BLOCKED. Never use the clipboard or print recovery words to tools/chat.
4. Launch the pinned browser in the reserved profile, loading every registered extension for that profile plus the new verified extension. Preserve other wallets and their native data. All wallets used together must share this one browser context. Follow the selected wallet's observed native create-wallet and backup path. Do not require MetaMask labels or assume every product has a recovery phrase. Use `fillWalletPassword` to fill native password fields from the encrypted record, without returning the password. Use social login, purchase or funding routes only when they are part of the requested setup. Discover controls from official version-specific source or non-secret UI; once a seed may be displayed, do not dump page text/button labels/ARIA/screenshot contents.
5. Reveal the newly created wallet's phrase through its intended native backup flow. In a single local script read only the ordered phrase-word locators and pass them directly to `captureRecovery`; do not return or display their values. The helper encrypts both password and words and verifies decryption before reporting saved. Complete native backup challenges with `fillRecoveryChallenge` using the actual 1-based word positions. Do not skip backup or mark it saved without verifying storage. Never generate a replacement phrase with a library/import flow.
6. Hide the phrase, finish onboarding and read the **full public account address** from the wallet's normal account/address UI. Do not derive addresses with an alternate signer, trust a truncated label or paste a made-up address. Call `completeWallet(ref, address, {family, validator})` with the selected chain family. EVM, Starknet and Fuel have built-in format checks; for Solana, Tron, Bitcoin, TON, Stellar and additional families reuse the app/vendor SDK's address validator. Format checks do not prove chain activation. See the Layerswap reference for its existing eight address providers. Store only public address/profile/extension metadata in the public result. Return address, chain family, wallet/version, profile reference and encrypted-backup location, never the password or words.
7. Register the completed named wallet with the shared session registry using the reservation’s profile, recording only public account/family, pinned browser/extension and private credential reference. Multiple distinct wallet extensions may share this profile; the runtime verifies compatible browser pins and serializes all access to it. For isolated scenarios also retain the scenario reason in public setup metadata. For the encrypted vault use credential kind vault with its reference and installed vault helper module path. Keep passwords/words out of the registry. Verify recovery-backup durability and actual address observation; optionally verify normal unlock using the saved password with recording off. Do not restore/import merely to test recovery unless requested. Close or lock the test wallet; hand the profile/public address to E2E tooling only on request. E2E tools get the password privately if needed, never recovery words.

## Failure and reporting

Creation is not idempotent. Keep a private provisioning journal identifying wallet ID/profile and password-prepared, wallet-created, recovery-saved, challenge-completed and complete stages. If interrupted after generation, retain the original profile and encrypted credentials; do not automatically create a second wallet or reset onboarding. Recover through that native UI only with the user's existing authorization. Missing/mismatched backup, ambiguous word order or unsupported layout is BLOCKED; never report a usable completed wallet from generated files alone.

For hardware/mobile/identity/multisig products, do not fabricate extension installation or export nonexistent recovery words. Prepare the correct official installation path and carry out available local steps; stop only for a genuinely missing device, passkey, organization/login prerequisite or transaction authorization. Label backup handling as user/device-managed when applicable. If deployment/activation is requested, execute it through the native wallet after checking the intended chain, account and fee; otherwise report the account as undeployed when applicable. Do not request permission for routine native creation/backup controls already authorized by the task.

Scripts use Node.js 22+ built-ins; the browser driver can reuse the project's Playwright. `node --test test/*.test.mjs` validates storage/security primitives with synthetic words; it does not prove an extension can create wallets. Actual creation success requires the real native flow and observed full address. The bundled workflow is agent-guided and adapts to the requested wallet. Unexercised native flows are reported unverified; broad discovery coverage is not a universal unattended onboarding guarantee.

Final response example: “Created your dedicated MetaMask test wallet. EVM address: <observed full public address>. Password and recovery words saved in the encrypted local vault at <path>; key reference: <path/name>. Funding/deployment: <observed outcome, or not requested>.” If only installing the skill, report the skill location and validation; do not invent an account address.
