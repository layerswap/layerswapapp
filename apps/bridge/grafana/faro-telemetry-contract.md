# Provisional Grafana Faro telemetry contract

**2026-09-11 transfer-step visibility:** the generic blocking and failure signals now cover the whole transfer step instead of one RPC case. New lifecycle step `transfer_blocked` (stage `wallet_action`, outcome `blocked`) is emitted once per reason transition wherever the send button is replaced by a message, with bounded `reason_code` values `rpc_unhealthy`, `same_account_required`, `wallet_unsupported_for_network`, `deposit_actions_unavailable`, `swap_error`, `insufficient_balance`, `insufficient_gas`, `gasless_unavailable`, `critical_price_impact`; it keeps its journey, is repeatable after recovery and has a 10-minute stall threshold. Wallet, network-switch, connection, transfer and gasless failures now carry a normalized `reason_code` (`user_rejected`, `insufficient_funds`, `gas_estimation_failed`, `contract_reverted`, `nonce_or_replacement`, `chain_not_added`, `wallet_disconnected`, `unsupported_method`, `invalid_parameters`, `internal_rpc_error`, `network_error`, `timeout`, `unknown_error`) with the raw provider code in the new `error_code` attribute; API error codes pass through unchanged. Multi-step wallet handlers can report failures through the new optional `onTransferError` prop. Form validation now codes every blocking message, so `validation_shown` covers no-source-route, invalid address, address-update-required and manual-transfer-unsupported. `widget_flow` snapshots gain `transfer_prompted` and `transfer_submitted`. The entry dashboard has a **Transfer step** tab and the Behavior funnel has Wallet prompted and Transaction submitted stages; two paused alert rules watch the blocked-or-failed share and quiet submissions. All of this is **Found only in source code** with local test evidence until deployed and observed in Loki.

Reconnect evidence at 14:11:00 UTC: [stored JSON](fixtures/faro-wallet-reconnect-loki-observed.json) contains a different account after disconnect/reconnect, with the same Faro session ID. Both addresses still match exact first-element historical lookups for that session. The prior address is absent from the new wallet snapshot. The journey ID changed between exemplars; do not claim journey preservation or infer the cause. This verifies reconnection with another account, not in-place account switching, arbitrary array membership, cross-session identity or outgoing payload fields.

The allowed verification states are:

- `Verified in Loki`
- `Verified in Tempo`
- `Verified in outgoing Faro payload`
- `Found only in source code`
- `Planned but not implemented`

`Verified in Loki` applies only to the named stored field and observed scenarios, not to all SDK variants or the full path through every boundary. The HTTP/error replay has paired outgoing and stored evidence. The later user-operated Sepolia lifecycle test has stored evidence only. Examples containing IDs are sanitized placeholders.

Loki names below are fields parsed from logfmt unless explicitly identified as stream labels. `| logfmt` puts extracted fields in the API result's `stream` object; that does not make them ingestion labels. Raw queries showed only `source`, `service_name`, and `detected_level` for the controlled records. No third tuple column containing structured metadata was returned.

Infrastructure update: the user supplied `layerswap/layerswap-fluxcd`; [the read-only infrastructure audit](faro-infrastructure-audit.md) pins the inspected revision and source links. `source="faro"` is explicitly supplied by Alloy's `loki.write.faro.external_labels`. Faro logs route directly from `faro.receiver` to that writer, bypassing the separately configured pod/OTLP processors. No custom Faro flattening/redaction/label-promotion stage is declared. Receiver logfmt serialization is consistent with the observed fields and documented default; exact installed-version behavior and runtime reconciliation remain unverified. Git retention/routing declarations do not upgrade any field to `Verified in Loki` or `Verified in Tempo`.

## Correlation contract, observed and proposed

Observed: a paired replay retained the exact session ID on both errors and all three fetch mirrors. The mirrors retained exact trace/span IDs in Loki. The errors had no active trace context. An equality query on traceID returned its one matching mirror. This verifies an event's own ID, not a causal relationship between an error and a nearby request.

The Sepolia test has one session and journey. Querying event_data_swap_id finds five later records; session_id plus event_data_journey_id finds all ten sequence values 1–10, including form submission and network switching before swap creation. Both are parsed fields, not stream labels.

A session/time match is a fallback: multiple quote/status requests, concurrent tabs, retries, and async callbacks make nearest-request selection ambiguous. A view_changed from unknown to / during initialization is observed; navigation between two distinct routes is not yet verified. No dedicated view ID was captured.

Proposed direct contract (not implemented): keep session.id through Loki and Tempo; attach journey_id and, once known, swap_id to meaningful application spans. Add trace/span IDs to lifecycle/error records only when there is a meaningful active causal span. Use bounded operation spans for quote request, swap creation, wallet connection, network switch, signature request and transaction submission; separate bounded deposit-detection and settlement polling episodes rather than one hours-long span or a span per trivial event. See the operation boundaries in Checkpoint B.

Tempo storage and links are explicitly deferred. For the approved reduced scope, navigation will be error group → affected session → timeline → Loki event. Dashboard variables, UI links, time range preservation and visual empty states still require implementation and browser testing after Checkpoint B approval.

## Privacy and label policy to decide before deployment

Do not promote these to Loki labels or metric dimensions: session ID, journey ID, swap ID, wallet addresses, transaction hashes, page/request URLs, reason text, error messages, span IDs, or trace IDs. They are high-cardinality investigation fields.

Candidate bounded dimensions, subject to controlled payload verification and production cardinality measurement, are application, environment, lifecycle stage/step/outcome, normalized reason code, network, token, path, action, and provider. Release/version is useful but grows with deployments.

User decision: retain useful wallet addresses alongside sessions and swap-form context as access-controlled searchable fields. Keep wallet family and connector, with optional wallet_chain_id; do not require wallet_network or infer the selected EVM chain from MetaMask alone. Connected-wallet synchronization is now implemented, not yet browser/backend verified: current addresses for connected wallets live in the JSON session field `connected_wallets`, distinct from source/destination form addresses. Code updates account/chain changes and clears disconnected records without overwriting swap context. Early startup metadata before the observer mounts can still contain SDK-persisted values; see the wallet implementation report. Addresses, swap IDs and transaction hashes must not become stream labels or metric dimensions. Fixtures replace these identifiers. Amount handling, sampling, console/resource capture, consent/opt-out, retention and access policy remain recommendations for approval; see Checkpoint B.

## Controlled-telemetry update procedure

For each captured scenario—initialization, route navigation, successful/failed/slow HTTP, uncaught and explicitly reported errors, wallet connection, signature rejection, lifecycle events, and Web Vitals—update the corresponding rows:

1. Save a sanitized raw browser request as a fixture and mark fields actually present as `Verified in outgoing Faro payload`.
2. Record signal count, batch/request endpoint, session/view IDs, and trace headers/IDs without treating the small sample as a distribution.
3. Inspect the receiver's Loki record independently. Tempo verification is deferred.
4. Replace assumed final names with observed names and mark `Verified in Loki` or `Verified in Tempo` as applicable.
5. Record observed boundary transformations. Attribute them to a particular Alloy component only when its configuration is available; do not infer component ownership from a stored field name.
6. Keep fields absent from the controlled capture at `Found only in source code`; absence in a single scenario is not proof of non-emission.

This contract must be reconciled again after enough production telemetry exists. Controlled telemetry can validate schema and linking mechanics, but not production baselines, thresholds, percentiles, volume, retention, cardinality at scale, query cost, or sampling effects.
