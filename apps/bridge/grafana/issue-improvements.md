# Issue investigation improvements

Updated 2026-09-10. This addresses the eight findings against the native development trial. Dashboard changes and frontend deployment are separate: publishing a Grafana query does not deploy the logging changes.

The main Issues view now includes **all unexpected errors**, including diagnostics, by default. Its Category column distinguishes explicitly reported user impact, diagnostics and unclassified records; a diagnostic category does not establish harmlessness. The Issues category dropdown offers All / User-impacting / Diagnostics / Unclassified. Test errors offers Include / Exclude / Only and labels the known controlled errors; it does not infer tests from a local release. These filters survive investigation and return navigation, and the selected row's category/test status scopes its occurrence count and trend.

The verified sample now shows **7 groups / 33 records** by default, or **5 groups / 31 records** with tests excluded. The previous two-row view was caused by excluding diagnostics. Large timestamp, volume and explanation cards were replaced with a compact two-unit status row and panel tooltips. The timestamp explicitly describes the selected range, not current collector health. [September 10 query verification](fixtures/faro-overview-visibility-verification.json) records all filter partitions and query checks. The current browser runtime failed during setup, so this revision is API/schema verified but has not received a new screenshot or click-through check.

Open [the development investigation dashboard](https://grafana-2.dev.lb.layerswap.cloud/d/layerswap-faro-trial-home). It has Issues, Recent failures, Journeys, Session lookup and Diagnostics tabs. Shared session investigation retains Timeline, Failures, Requests and Context.

## Source-map acceptance check

Use a deployed build with an identified release and a known controlled throw location. Confirm its outgoing Faro `app.version`, bundle URL, line and column; then inspect the stored exception and verify the mapped original source file, line and function against that exact build artifact. Confirm the running Alloy receiver's mapping/download configuration and artifact availability. Generating or uploading maps alone is insufficient. The existing local artifact check and infrastructure audit do not supply this evidence.

The receiver supports its own [source-map configuration](https://grafana.com/docs/alloy/latest/reference/components/faro/faro.receiver/). The existing upload plugin's configuration is not proof that this self-hosted receiver can resolve its artifacts. No claim of source-level attribution should appear in the view until the end-to-end check passes.

## Alert review and issue state

`faro-issue-alerts.paused.json` is a Grafana **file-provisioning artifact**, not an imported dashboard. All three rules are paused. It creates no contact points or notification policies. Choose the recipient/contact point and tune thresholds to actual traffic before enabling; in quiet development, no telemetry is expected without a controlled canary. The comparison rule means absent from the preceding retained 24 hours, not first-ever or regressed. Query errors/no-data states remain explicit; a zero error-series fallback cannot prove the collector is healthy.

The paused error alerts retain their earlier non-diagnostic scope; expanding the dashboard's default visibility did not enable or broaden notifications. Revisit that scope explicitly during alert review.

The static alert queries use the same normalization as the dashboard but omit interactive variable plumbing. The original repeated comparison query exceeded the Loki gateway's URI limit; the compact form passed live validation.

For assignment/resolution, retain a separate durable issue record keyed by application + API/deployment scope + fingerprint version/key, with owner, status, resolution release and audit history. Use an existing issue tracker/Sentry if that workflow is needed; adding fake resolved controls to a Grafana dashboard would lose state and misrepresent recovery. No new service or Sentry SDK was added without a chosen workflow. [Grafana provisioning](https://grafana.com/docs/grafana/latest/alerting/set-up/provision-alerting-resources/file-provisioning/) and [missing-series behavior](https://grafana.com/docs/grafana/latest/alerting/guides/missing-data/) explain why alert disappearance is not reliable issue resolution.

Query-time normalization and timestamps use the documented [LogQL template functions](https://grafana.com/docs/loki/latest/query/template_functions/). All high-cardinality IDs remain event/query data; none were promoted to ingestion stream labels. Production-scale query latency and cardinality still need representative testing.
